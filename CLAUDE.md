# AdvoAI — Project Context

## Summary

AdvoAI is a conversational legal assistant for Uzbekistan: hybrid parent-child RAG over the legal corpus (`lex.uz`-sourced codes/constitution), Gemini-based generation, contract drafting, document comparison. Two sibling repos:

- **AdvoAI-backend** — FastAPI. Deploys to a Hugging Face Space via a `space` git remote in addition to `origin` (GitHub).
- **AdvoAI-frontend** — Next.js.

The two deployments are cross-origin (frontend's own domain vs. the HF Space), which shapes several decisions below (auth token delivery, CORS, download proxying).

For implementation detail beyond what's here, see the working plan: `/home/doniyor/.claude/plans/i-need-you-to-mellow-whale.md`.

## Done

- **Sliding JWT renewal** (`app/middleware.py`): `get_current_user`/`require_auth`/`require_admin`/`require_root_admin` now take an optional `Response` and reissue the token when less than 24h of its 72h life remains, returned via `X-Renewed-Token` (already exposed cross-origin — `Access-Control-Expose-Headers: *` in `main.py`) and an updated cookie. Frontend `authFetch.ts` picks up that header on every call and persists the new token; `AuthContext.tsx`'s own mirror cookie now derives its `max-age` from the JWT's real `exp` claim instead of a hardcoded 7 days. Root cause of "logged out constantly": a fixed-lifetime token with no renewal path at all, compounded by the frontend's cookie outliving the token it wrapped.
- **Removed the LLM-authored trilingual sources heading** (`prompts.py`, Mode A instruction 5): the model no longer writes its own "Manbalar / Источники / Sources" section — the frontend's `SourcesDropdown`/`WebSourcesDropdown` (already localized, favicon'd) is the only source list now. Inline natural references ("According to Article 5...") are still fine.
- **Sidebar silent-fallback fixes** (`InsightPanel.tsx`): three paths that used to render a bare, unstructured chunk with no explanation now have explicit states — an empty successful parts fetch is treated as an error; a citation with no id resets stale state instead of leaving a previous citation's parts on screen; an invalid/stale `part_id` still shows the document but with a visible "couldn't locate the exact cited section" notice (new locale key `insight.cited_part_missing` in all 3 languages).
- **True-citation highlighting** (Batch 2): `context_markdown` is rebuilt in `chat.py` right before the LLM call with a `[REF n]` tag per retrieved part, numbered in the exact order `_build_citations` iterates `parent_documents` — this gives the model a stable handle to cite without exposing internal ids. A new UNIVERSAL CORE REGULATION 7 in `prompts.py` has the model end its raw output with a hidden `<!--CITATIONS:[{"ref":1,"quote":"..."}]-->` block (never shown to the user) naming which REFs it relied on and a short verbatim excerpt for each. `_extract_citation_quotes` (`chat.py`) strips that block from the visible answer and resolves ref numbers back to `part_id`s; `_build_citations` then drops any retrieved-but-unquoted part instead of showing it as if it were used, and attaches the `quote` to citations that were. A missing/unparseable block falls back to citing only THIS TURN's own fresh matches (`fresh_ids`), never the whole merged memory window (see Batch 3) — a model formatting slip must never surface a part from turns ago that this specific answer never touched. Frontend (`InsightPanel.tsx`) highlights `quote` when present, falling back to whole-part matching against `text` otherwise. Covered by `tests/test_citation_quotes.py`.
- **Session chunk memory** (Batch 3): new `session_chunk_memory` table (schema V7/V8) caches retrieved parts' real content per session — `part_id`, full `parent_documents`-shaped metadata, `text`, and `message_id` (which chat_messages row fetched/re-matched it). `chat_sessions.chunk_memory_turn` is a per-session counter that advances once per fresh-retrieval (non-conversational) turn only — NOT per message, NOT wall-clock. Per turn: bump the counter → prune anything untouched for `CHUNK_MEMORY_WINDOW` (3) turns → load the surviving window → run vector search with `already_cached` (skips the `document_parts` text fetch in `rag_pipeline.retrieve_context` for ids already in memory — the actual "don't re-hit the DB" half of the original ask) → merge memory + this turn's fresh matches (fresh copies win) into `parent_documents` → upsert only the fresh/re-matched ones (memory-only riders don't get their LRU clock touched) → backfill `message_id` once the user's chat_messages row is pre-saved. Conversational turns read the window (`get_session_chunk_memory`) and inject it as plain prose via a new `memory_markdown` param on `client.ask()`/`CONVERSATIONAL_PROMPT_TEMPLATE`, with a "Session Memory Exception" carve-out in `prompts.py` Mode B's law-quoting ban — no bump, no prune, no citation UI. Guests (no session row) keep today's stateless behavior. `top_k` hard-clamped to 5. `delete_document` sweeps orphaned rows via `sweep_orphaned_chunk_memory`. Web/URL results are never cached here (synthetic non-uuid ids, ephemeral content) — see Findings. Fully verified against the live Neon DB (schema apply, insert/prune/LRU-refresh, and a full route-level round trip with the DB pool live), not just mocked tests — see `tests/test_session_chunk_memory.py` and `tests/test_rag.py`.
- **Autocompaction** (Batch 3b): `delete_oldest_message`/`MAX_WINDOW_MESSAGES` retention is gone — every `chat_messages` row is kept forever, both `sessions.py`'s `/{id}/messages` endpoint and `chat.py`'s per-turn fetch now pull everything not yet summarized (`_unsummarized_messages`, bounded only by a generous `MESSAGE_FETCH_CEILING` safety ceiling shared between the two, not a design cap). `chat_sessions.summarized_through_message_id` (schema V9) tracks the newest message already folded into `session_summary`, so a compaction pass only ever folds genuinely new messages. Trigger: `GeminiClient.estimate_tokens` (a real Gemini `count_tokens` call, gated behind a cheap char-length pre-check so short chats never pay for it) measures `session_summary + chunk-memory text + unsummarized history`; over ~500k (`AUTOCOMPACT_TOKEN_THRESHOLD`), `_background_history_maintenance` finds the oldest still-resident chunk-memory row's `message_id` (the anchor), keeps `AUTOCOMPACT_VERBATIM_BUFFER` (5) messages before it plus everything from the anchor onward verbatim, and folds only the prefix before that into the archive summary via the existing (reworded — see Findings) `summarize_archive`. Currently moot in production (`override_prompts_enabled` is `false` on the live DB) but was a live landmine. ## Batch 5 — status events + word-chunk replay (revised scope)

Genuine token-level streaming was scoped and rejected first — see the reasoning preserved below, since it still applies to `ask()` itself. What shipped instead: the full answer is still generated server-side in one shot (so tool-call detection, the hidden citation-quote block, and `ref_quotes` all work exactly as before Batch 5), then the *response* is streamed to the client two ways:

- **`status` SSE events** ("searching_corpus" / "searching_web" / "drafting") fire before each slow step (`retrieve_context`, `perform_web_search`, `_run_generate_contract_tool`) so the wait is never silent — this is the actual latency-perception fix, and needed no change to `ask()`.
- **`delta` SSE events** replay the finished answer in ~3-word chunks (`_stream_answer_text`, `chat.py`) with a small `asyncio.sleep` between them, purely for the incremental-reveal UX (styled after Claude's own reveal — word-by-word text plus a small rotating indicator that sits below the text while generating, `GeneratingIndicator` in `MessageBubble.tsx`). This is honestly a replay, not true streaming — documented as such, not hidden.
- `citations` and `done` (terminal, carries session_id/model_used/intent/metadata/attachments) fire after the deltas, since both still depend on the complete answer.
- `POST /api/chat/` is now `StreamingResponse` (`text/event-stream`); session/attachment-ownership validation stays in `ask_advoai` (still returns real 403/500 before the stream starts), everything else moved into `_generate_chat_stream`, whose own try/except turns a mid-generation failure into a terminal `error` SSE event instead of an HTTP error status (locked to 200 once headers are sent). `X-Accel-Buffering: no` is set so an nginx-fronted deployment (the HF Space) doesn't buffer the whole response before delivering it.
- Frontend (`useChatManager.ts`): `sendToBackend` now owns the assistant message end-to-end — creates a placeholder (`isStreaming: true`), reads `res.body.getReader()`, and patches the message in place per SSE event; callers (`handleSendMessage`, the pending-question effect) only need the resolved `session_id` for their own bookkeeping. A message mid-stream is excluded from the localStorage persistence effect (would otherwise thrash on every chunk) and stripped of `isStreaming`/`statusLabel` by `serializeMessages` so a reload can never resurrect a stream nothing will finish.
- Verified: full backend suite (93 tests, including two new SSE-contract tests in `test_chat_route.py`), `tsc --noEmit` clean, and a real end-to-end run against the live local backend (`curl -N` and a Node `fetch()` script using the exact same frame-parsing logic as the frontend) confirming the `status → delta × N → citations → done` event sequence over a real network connection with a real Gemini answer. **Not yet visually verified in an actual browser** — the Claude-in-Chrome extension was unavailable in this session, so the fade-in/indicator UI itself (as opposed to the data flowing correctly) has not been eyeballed. Worth a manual pass before calling the UI polish "confirmed," per the verify-before-done rule below.

### Why true token-level streaming (of `ask()` itself) was rejected

The plan's original design predates Batches 2–3 and no longer fits what shipped:

- **`ask()` sends `tools=[generate_contract]` on every single call** — whether a response is prose or a function call is unknown until enough of the stream is consumed to tell, so any implementation must buffer first, not stream from byte one.
- **The hidden `<!--CITATIONS:[...]-->` block (Batch 2) would render to the user** if raw deltas were streamed — it's stripped from the *complete* answer today; streaming needs the same tail-suppression, which means buffering the tail at minimum.
- **Citations can no longer be sent "immediately."** The plan assumed citations were available pre-generation; since Batch 2 they depend on `ref_quotes`, parsed out of the finished answer.
- **`_generate_with_retry`'s key-rotation/backoff ladder retries a *completed* call.** It has no way to retry or resume a half-emitted stream.

Honest token-level streaming here would still mean buffering the full response server-side and replaying it — which is exactly what the status+replay design above does deliberately and transparently, instead of pretending otherwise.

## Findings

- R2 (Cloudflare) has no CORS policy by default — hence the `/api/chat/file/{key}/raw` same-origin proxy route for docx preview/download instead of fetching the presigned URL directly from the browser.
- FastAPI matches routes in registration order; a greedy `:path` route registered early can silently swallow requests meant for a more specific route registered later.
- Retrieval is whole-document-part granularity (parts run 20k+ chars) — a citation's `text` today is the entire part, not the sentence actually used, which is why sidebar highlighting lights up the wrong span (fixed by Batch 2's verbatim-quote approach).
- Retrieved chunk text is never persisted into `chat_messages`/conversation history today — only the model's own prose answer is replayed on follow-up turns (`llm_client.py` history replay). `safe_citations_for_storage` deliberately strips `text` before persisting citations. This is why a naive "just filter by citation id already seen" dedup would have been silently unsafe (Batch 3's `session_chunk_memory` fixes this by storing content, not just ids).
- ~~The existing background task (`chat.py`) permanently deletes rows via `delete_oldest_message`...~~ **Resolved in Batch 3b**: `delete_oldest_message` and `MAX_WINDOW_MESSAGES` are removed entirely (the function no longer exists in `queries.py`); every `chat_messages` row is kept forever. `LLM_HISTORY_MESSAGES`'s old fixed-12 replay cap is gone too — replaced by `_unsummarized_messages` (everything not yet folded into `session_summary`) — so "which of the two knobs" is no longer an ambiguity to track.
- Making the LLM text-replay window unbounded (Batch 3b) has a sharp edge: `llm_client.py`'s history replay rehydrates attachments (`build_parts` — an R2 fetch + Gemini file-handle mint, or a full-text inline) for every historical user turn carrying `document_ids`. Left unbounded, a document-heavy session would re-rehydrate every attachment on every turn until compaction fires at ~500k tokens — real latency/cost, and a plausible 413 well before then. Fixed by decoupling: `GeminiClient.ATTACHMENT_REHYDRATION_WINDOW` (12) bounds *rehydration* independently of the now-unbounded *text* replay. Caught by the advisor before ship, not by a test — worth remembering that "make X unbounded" always deserves an explicit check for what X drags along with it.
- DuckDuckGo is non-viable as a free web-search provider (from prior investigation); Brave has dropped its free tier. Current provider order: Exa → Tavily → Serper.
- The `/full/meta` endpoint (`documents.py`) already returns the authoritative full list of a document's `part_id`s, so the frontend can and does detect a stale/invalid cited `part_id` client-side without a separate backend validation call.
- The DB in `.env` is a live Neon instance, not local — `scripts/run_schema.py` was run against it (with explicit user confirmation) to verify Batch 3's schema; it's additive/idempotent (`CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`), matching the existing V1–V8 convention in `schema_unified.sql`. Note `CREATE TABLE IF NOT EXISTS` is a no-op against an already-created table — a column added to that table's definition later (V8's `message_id`) needed its own separate `ALTER TABLE ADD COLUMN IF NOT EXISTS`, not an edit to the original `CREATE TABLE`.
- Web-search and fetched-URL results carry synthetic, non-uuid `id`s (`web-{provider}-{idx}`, `url-{idx}`) — anything touching `session_chunk_memory`'s `part_id::uuid` column must filter these out first (`_is_uuid` + `kind == "corpus"` in `chat.py`), or Postgres throws on the cast and 500s the whole request. Caught by `tests/test_session_chunk_memory.py::test_web_search_results_are_not_upserted_into_chunk_memory`.
- `rag_pipeline.retrieve_context`'s vector search step can never be skipped (it's what tells you which parts are relevant to THIS question), but the subsequent `document_parts` text fetch can be, per-id, via its `already_cached` param — this is the real "don't re-load the same chunk from the DB" mechanism, distinct from (and in addition to) not re-injecting the same text twice into the prompt.
- The plan's "restrict to the primary domain tier only when clearly regulatory, otherwise don't hard-restrict" distinction was simplified: since web search here only ever fires for `legal_rag`-intent turns (conversational/document_request never trigger it), every web-search-triggered query is regulatory by construction, so both confirmed tiers are always passed to Exa's `includeDomains` together. Also: Exa has no "soft preference" domain parameter — `includeDomains` is a hard filter — so the "prefer official over secondary" ranking is expressed only via the prompt instruction, not the API call. Revisit if a future need arises for genuinely unrestricted web search (e.g. a non-legal-domain feature).
- `get_current_user`/other auth dependencies are called directly as plain functions in several `auth.py` routes (not via FastAPI `Depends()`), so `app.dependency_overrides` can't intercept them in tests — a real signed JWT (`create_access_token` + `Authorization: Bearer`) is required to exercise those routes, not a dependency override.
- Minting a real JWT for a live-DB round trip outside pytest needs `await init_pool()` called first — `get_connection()` raises `RuntimeError` otherwise, since the pool is normally initialized by FastAPI's own startup hook, not on import.
- `regenerated_from_id` always pointing at the chain's ROOT (never the immediately-previous variant) is what keeps "list every variant" a single `WHERE id = root OR regenerated_from_id = root` query — pointing it at the previous sibling instead would need a recursive walk to find every variant, for no benefit.

## Rules

- **Audit existing code against intent before reusing it — never inherit as-is.** Read the mechanism, confirm it still matches what's wanted now, and say plainly if it doesn't. This already caught the `delete_oldest_message` conflict above.
- **Nothing is ever deleted.** Every `chat_messages` row is kept forever; "compaction" means summarizing what's sent to the LLM, never truncating or dropping stored messages. Full history always renders in the UI.
- **No hard character/token ceiling on retrieved legal chunks.** They're structured text (moddas/articles) that must never be truncated mid-clause. Size is controlled by window size (5 messages) and autocompaction (~500k tokens), not by a char cap.
- **Confirmed settings:** `top_k` clamped to 5 per turn; session chunk memory window = **3 fresh-retrieval turns** (`CHUNK_MEMORY_WINDOW` in `queries.py`, revised down from an initial 5 after verifying worst-case memory volume — see Findings), LRU eviction; autocompaction trigger ≈ 500k tokens, preserving the memory window + the 5 messages immediately before its anchor, verbatim; web search is router-decided with the user toggle as veto-only, persisted per-account in the DB; Exa domain bias — primary/official tier `lex.uz, gov.uz, prezident.uz, parliament.gov.uz, senat.uz, minjust.uz, soliq.uz, cbu.uz, stat.uz`, secondary/reputable (prefer, not restrict) `norma.uz, kun.uz, gazeta.uz, spot.uz`.
- **Conversational (memory-grounded) turns keep today's UI**: no citation dropdown, no quote mechanism — the model may write an inline "Manbalar" mention only when genuinely load-bearing, and must never cite anything outside the chunks actually injected into that turn's context.
- **Verify before marking done.** Run the relevant tests, exercise the actual UI/endpoint, don't just read the diff and assume it works — especially for streaming, which must be checked against the real deployed HF Space, not only local dev.
- **Update this file at the end of every batch**, then copy it into both `AdvoAI-frontend/CLAUDE.md` and `AdvoAI-backend/CLAUDE.md` in the same commit as the code it describes.
